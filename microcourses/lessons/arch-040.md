# 计算机体系结构 · 第40课
## HBM内部组织与先进封装：Channel、Pseudo-channel、TSV及带宽利用率

**2026年11月28日｜第6周第5节新课｜约16分钟（测评另计）**

## 一、动机：为什么HBM很宽，却不保证每次访存都很快？

前几课已掌握ACT/PRE、控制器调度、DDR接口和刷新。今天从GPU视角看HBM。假设一个Stack提供约1.2TB/s带宽，单条32B依赖读的端到端延迟仍为200ns，那么单链带宽只有32/200=0.16GB/s。高带宽依赖许多独立访问同时进行；它不是单次读延迟的倒数。HBM通过封装增加可用数据线，再通过多个Channel、Pseudo-channel（PC）和Bank将流量分散。问题是如何真正用满这些资源。

## 二、物理结构：TSV与Interposer（2分钟）

典型2.5D集成中，GPU Die与HBM Stack并排位于硅中介层或其他高密度封装互连上。HBM内部多层DRAM Die通过TSV（硅通孔）和层间连接形成垂直通路，Base Die负责相应接口、逻辑或信号连接，具体实现随产品变化。

~~~text
                HBM Stack
               ┌───────────┐
               │ DRAM Die  │
               ├─┆─────┆───┤
               │ DRAM Die  │
               ├─┆─────┆───┤
               │ DRAM Die  │  ┆ TSV
               ├─┆─────┆───┤
┌───────────┐  │ Base Die  │
│ GPU / PHY │  └───────────┘
└─────┬─────┘        │
══════╧══════════════╧══════  Interposer / 高密度封装互连
        大量短距离并行数据线
~~~

TSV主要提供垂直连接，Interposer主要提供GPU与HBM之间的横向高密度连接。不是每一层DRAM都有一套可叠加到GPU上的完整外部接口。8-high到12-high主要增加容量（同Die密度下约1.5倍），不必增加接口宽度或峰值带宽。

短互连有机会降低每比特传输能量。若平均动态传输能量为e pJ/bit，物理带宽为X TB/s，则I/O动态功率约为8eX W，因为1TB/s=8×10^12 bit/s。例：e=2、X=3时为48W。这是教学模型，不含阵列、刷新、控制器与静态功耗。堆叠还面临热阻、温度、供电、封装良率和成本约束；不能把高集成度当作无限扩展。

## 三、Channel与Pseudo-channel到底有什么不同？（3分钟）

| 组织 | HBM2/2E常见PC模式 | HBM3/3E |
|---|---:|---:|
| 每Stack数据宽度 | 1024 bit | 1024 bit |
| Channel数 | 8 | 16 |
| 每Channel宽度 | 128 bit | 64 bit |
| PC数 | 16 | 32 |
| 每PC宽度 | 64 bit | 32 bit |
| 常见完整Burst | BL4 | BL8 |
| 每PC的Burst负载 | 32B | 32B |

HBM3并非通过把1024根数据线翻倍来增加PC数量，而是把接口划分得更细。PC通常有各自的数据路径与可独立管理的存储资源，但仍可能共享部分命令/地址、时序、刷新或功耗资源。不能把它视作完全独立的物理内存设备。AMD的HBM2类控制器文档明确描述两个PC共享命令/地址/控制总线；HBM3的具体共享约束应以其规范及控制器实现为准。

~~~mermaid
flowchart TD
 G["GPU SM / L2"] --> N["片上互连与地址路由"]
 N --> S["HBM Stack"]
 S --> C0["Channel 0：64 bit"]
 S --> C1["Channel 1...15"]
 C0 --> P0["PC0：32 bit"]
 C0 --> P1["PC1：32 bit"]
 P0 --> B0["Banks / Rows"]
 P1 --> B1["Banks / Rows"]
~~~

定义S为Stack数量，W为每Stack有效数据宽度(bit)，r为每引脚数据率(Gb/s)，m为每Stack PC数，b为一次PC事务字节数。带宽用十进制单位，1B/ns=1GB/s。

$$
BW_{\rm stack}=Wr/8,\qquad BW_{\rm total}=SWr/8
$$

例：HBM3E教学参数W=1024、r=9.6，单Stack=1228.8GB/s，16个Channel各76.8GB/s，32个PC各38.4GB/s，4个Stack合计4915.2GB/s。注意r已经是数据率，不再乘2。Micron的HBM3E产品页面标称单Stack超过1.2TB/s，提供24GB 8-high及36GB 12-high版本；教学计算不是对每款产品的精确规格承诺。

相对于第38课的DDR5-6400 64-bit等效接口51.2GB/s，上述单Stack带宽是24倍，但不能据此推出随机访问延迟是1/24。

## 四、地址映射与Partition Camping（3分钟）

教学模型：32个PC、每个PC宽32 bit、r=8 Gb/s，每个PC峰值32GB/s。一次事务32B，令i=floor(address/32)，PC(i)=i mod 32。忽略Stack/Bank其他映射、时序和缓存。

若连续访问i=0,1,2,...，32个PC都能获得流量。若步长s=8，则访问序列为0,8,16,24,0,...，只有4个PC活跃。这种请求集中在少数内存分区的现象常被称为Partition Camping。

| 事务步长s | 活跃PC数 | 理想物理带宽上界 |
|---:|---:|---:|
| 1 | 32 | 1024 GB/s |
| 2 | 16 | 512 GB/s |
| 4 | 8 | 256 GB/s |
| 8 | 4 | 128 GB/s |
| 32 | 1 | 32 GB/s |
| 33 | 32 | 1024 GB/s |

访问序列第k项为(ks) mod m。重复起点需要m整除ks。设d=gcd(m,s)，约分后m/d与s/d互素，所以最小正周期为m/d；周期内没有重复。因此：

$$
m_{\rm active}=\frac{m}{\gcd(m,s)},\qquad BW_{\rm physical}\le m_{\rm active}\frac{Wr}{8m}.
$$

这个公式只适用于上述简单模映射与固定步长。真实GPU可能使用XOR哈希、多级交织、地址重映射等方式。可尝试改变数据布局、padding、tile形状或调度，改善分区负载。比如在教学模型中将步长32改为33，活动PC数从1变32；但padding增加空间或流量，不能直接保证端到端加速。即使XOR也存在冲突模式，测评将检验这一点。

若PC j的流量比例为p_j、服务上限为c_j，则总物理流量X必须满足p_j X≤c_j。因此一般上界是min(c_j/p_j)，只考虑p_j>0的PC。这个约束比只数活跃PC更适合不均匀流量。

## 五、GPU访存合并：传输了多少字节，真正用了多少？（2分钟）

Warp可以暂时理解为共同执行一条指令的一组32个线程。以32B对齐事务、32个线程各读4B为教学案例。NVIDIA CUDA指南对计算能力6.0及以上的访存合并给出了32B事务的解释。这里假定所有事务都到达HBM且没有缓存复用。

~~~text
连续访问：线程0..7   线程8..15   线程16..23  线程24..31
          [32B全用]   [32B全用]   [32B全用]   [32B全用]
分散访问：[4B使用|28B未用] [4B使用|28B未用] ... 共32段
~~~

若连续、对齐，只需4个32B事务，128B全部有用。若相邻线程地址相差64B，每个线程落在独立事务，需32×32=1024B，但仍只有128B有用。

$$
\eta=\frac{D_{\rm useful}}{D_{\rm physical}},\qquad
BW_{\rm useful}=\eta BW_{\rm physical}.
$$

若物理带宽均为800GB/s，连续访问的有用带宽为800GB/s，分散访问仅100GB/s。缓存命中、跨Warp复用、写掩码等会改变实际HBM流量；不能直接将GPU事务计数等同于物理HBM总线事务。访存合并改善字节效率，地址映射改善资源均衡，两者不同，甚至可能相互冲突。

## 六、MLP与带宽利用率：为什么需要数千个在途请求？（3分钟）

设K为最多在途的32B事务，L为平均占用时间(ns)。由Little定律N=lambda L，N≤K，得到物理带宽上界Kb/L。加入PC分布、总线及控制器限制：

$$
BW_{\rm physical}\le\min\left(\frac{Kb}{L},\min_{j:p_j>0}\frac{c_j}{p_j},BW_{\rm other}\right).
$$

例：上述1024GB/s Stack，b=32B，L=200ns，想达到峰值，至少需要K≥1024×200/32=6400个在途事务。如果只能维持2048个，则MLP上界327.68GB/s；若同时只有4个PC活跃，综合上界为128GB/s。K是该统计层级的实际在途事务容量，不是线程数或Warp数。

这解释了GPU为何依靠大量活跃Warp、独立访存指令和流水线隐藏延迟。更大并发也可能增加排队，使L变大；以上是给定L的必要条件，而不是吞吐保证。Bank冲突、tFAW、列命令间隔、刷新、读写切换和温度降频等仍会进一步限制吞吐。

## 七、联系LLM推理：权重带宽与KV Cache带宽（2分钟）

假设一款教学GPU实际可供模型使用的HBM物理带宽上界为3TB/s，一个Decode Step需要从HBM读12GB权重（Batch内共享），每个序列额外读0.25GB KV，batch大小为B。忽略计算、写入、通信和其他流量，且所有字节必须经同一HBM瓶颈。

$$
T_{\rm step}\ge (12+0.25B)/3\ \text{ms},\qquad
\text{Token/s}\le\frac{3000B}{12+0.25B}.
$$

| Batch | 每步HBM流量 | 延迟下界 | 聚合Token/s上界 |
|---:|---:|---:|---:|
| 1 | 12.25 GB | 4.083 ms | 244.9 |
| 8 | 14 GB | 4.667 ms | 1714.3 |
| 32 | 20 GB | 6.667 ms | 4800 |

Batch增加摊薄权重流量，但KV流量随序列数增加。在这个固定KV流量模型下，形式上的吞吐渐近上界为12000 tokens/s，并不代表可以使用无限Batch：显存容量、计算能力、延迟SLO和并发资源会限制它。线性注意力可能消除传统KV随上下文增长的问题，但仍有权重和Recurrent State流量。更高HBM峰值也不能修复不合并访问或分区热点。

## 八、实验、反例与内存语义边界（1分钟）

设计固定工作量的微基准：连续/跨步访问、不同对齐、不同独立流数、padding与布局变化；分别记录每PC/分区流量（若硬件支持）、物理与有用字节、在途请求、L2命中、延迟、吞吐及温度/频率；仿真还可观察ACT、PRE、刷新和Bank冲突。固定时钟、工作集、读写比例和测量口径。不能把所有低带宽都归咎于HBM，也不能仅用虚拟地址推断真实PC映射。

重申：CPU TSO的经典Store Buffering (0,0) 是Store Buffer传播和Store→Load排序的结果，不由DDR/HBM服务顺序决定。GPU也有自己的内存模型、原子操作与同步作用域；不能直接套用x86-TSO。Store退休、相干可见与DRAM写回是不同事件，高带宽与一致性保证无关。

首次不公布答案。前三题客观评分，第四题依据Rubric审阅。80分及以上进入下一专题，60—79分补一例，低于60分重点回顾再练；既定课程编号不变。

### Lv1｜PC细分与接口带宽（15分，单选，2分钟）

在同一1024-bit HBM接口、相同每引脚数据率下，将16个64-bit Channel各拆成两个32-bit Pseudo-channel。下列哪项最严谨？

A. 理论总数据带宽翻倍，因为独立队列数量翻倍。

B. 每个PC都可以使用原Channel的全部64根数据线。

C. 总数据线宽度不变，峰值不变，但更细粒度调度可能提高实际利用率。

D. 所有命令、刷新和功耗约束从此在PC之间完全独立。

可选提示：区分数据线数量和请求调度资源数量。

### Lv2｜步长映射与物理带宽（20分，数值，4分钟）

一个教学HBM Stack有32个PC，每个PC宽32 bit、引脚速率8 Gb/s。32B请求的编号i=floor(addr/32)，PC(i)=i mod 32。持续访问i=0,12,24,36,...，各活跃PC负载均衡且都能达到峰值，其他限制忽略。求这条流的物理带宽上界（十进制GB/s）。

可选提示：先求模32的访问序列周期，再乘单PC的带宽。

### Lv3｜访存合并与资源映射（25分，多选，5分钟）

教学GPU中一个Warp有32个线程，每线程读取不同的4B，32B对齐事务；所有事务均到达HBM且无缓存复用、压缩或合并后的额外变化。对比连续4B步长、32B步长及PC组织，选择所有正确陈述。

A. 若基地址32B对齐，连续4B步长需要4个事务。

B. 32B步长需要32个事务，但每个事务中的32B全部是程序有用数据。

C. 32B步长的有用字节比例为12.5%。

D. 若实际物理带宽相同且只考虑该流量，连续访问的有用吞吐可为32B步长的8倍。

E. 连续访问形成的4个事务必然分布在4个不同的HBM Stack。

F. PC负载均衡与Warp访存合并属于不同层次，改善其中之一不能自动保证另一项最优。

可选提示：分别统计有用字节、传输字节以及物理地址映射，避免把事务数等同于Stack数。

### Lv4｜模映射证明、XOR反例与性能诊断（40分，开放，10—12分钟）

教学HBM有32个PC，每个32-bit、每引脚8 Gb/s，32B事务。A（12分）：对PC(i)=i mod 32，证明任意正整数步长s访问的不同PC数为32/gcd(32,s)，并分析s=16、32。B（10分）：改用PC(i)=(i XOR floor(i/32)) mod 32。分析从i=0开始的前32次访问，分别取s=32、33，说明为何XOR不保证所有模式均衡。C（10分）：对均衡流量，平均占用时间200ns、最多4000个在途32B事务；每个事务只含8B有用数据。求物理与有用带宽上界、达到全Stack峰值所需最少在途事务数；若合并后每事务有用32B且其他参数不变，重新计算有用上界。D（8分）：设计对照实验区分地址映射热点、访存合并不足、MLP不足、刷新/热限制，并说明HBM服务顺序不能代替ISA或GPU同步作用域的正确性证明。

可选提示：A找最小正周期；B直接分析低5位；C统一物理与有用字节口径；D分别改变一个因素。
