## 第五周综合复盘：低 FLOPs、低显存与低延迟为什么不是一回事？

前六课依次学习 Prefill/Decode、Continuous Batching、PagedAttention/Prefix Caching、KV 量化/卸载、权重与激活量化、Speculative Decoding。今天不引入第七种优化，而是建立一套**先诊断瓶颈、再选优化、最后用同质量与 SLO 实验验证**的统一思路。

学习目标：①推导 KV、分块和 Decode 的资源公式；②联系排队、算力/带宽与 TTFT/TPOT；③区分数据复用、压缩与减少顺序验证轮次；④设计不误报加速的公平实验。

## 一、先画清楚一次生成请求的数据流

~~~mermaid
flowchart TD
  A["请求到达 / 排队"] --> B{"已有可复用的完整前缀 KV？"}
  B -->|否| C["Prefill：并行处理已知 Prompt"]
  B -->|是| D["跳过可安全复用的前缀计算"]
  C --> E["将各层 K/V 写入 KV Pool"]
  D --> E
  E --> F["输出第 1 个 Token：TTFT 截止"]
  F --> G["Decode：新 Query 读取历史 K/V"]
  G --> H{"生成结束？"}
  H -->|否| I["调度下一轮 / 可选 Speculative Verify"]
  I --> G
  H -->|是| J["释放活跃引用；可保留合法前缀缓存"]
~~~

**Prefill** 可以并行计算已知 Prompt 的多个位置，但仍受 Causal Mask 约束；**Decode** 的未来 Token 尚未知，同一请求存在自回归顺序依赖。不同请求之间可通过 Continuous Batching 并行。

KV Cache 通常保存历史 Key/Value，而不是整个 Attention 概率矩阵。它避免重复运行历史网络层，却不意味着新 Query 不再读取历史 KV。

## 二、显存：从 GQA 公式到真正的 KV Block 占用

设 L 层、Hkv 个 KV Head、每头 dh 维、B 条各缓存 T 个 Token、每元素 b 字节。全量历史的 KV Payload 是：

\[
\boxed{M_{\mathrm{KV}}=2LBTH_{\mathrm{kv}}d_hb}
\]

系数 2 来自 K、V 两份；GQA 的 KV 头数不是 Query 头数。在模型与头维等其他条件相同的近似比较中，Hkv 从 32 变为 8，KV Payload 降为四分之一，但端到端推理速度不保证四倍。

**手算例：** L=32、Hkv=8、dh=128、T=2048、B=12、b=2（BF16）。一个 Token、一个请求占用 \(2\times32\times8\times128\times2=131072\) B，即 128 KiB；每请求 256 MiB，12 请求合计 **3072 MiB（3 GiB）**。这只是 KV Payload，未计权重、分片、页内碎片或临时缓冲。

若每页容纳 g 个 Token，无共享时独占请求 i 的物理页数：

\[
n_i=\left\lceil\frac{T_i}{g}\right\rceil,\quad
w_i=gn_i-T_i,\quad0\le w_i<g.
\]

w_i 是末页空槽，属于**内部碎片**；分页改善的主要是连续分配与外部碎片管理。开启共享后，实际物理页数要数唯一物理块，不能把所有请求的逻辑页数直接求和。

前缀缓存通常只安全复用**完整且上下文一致**的历史块：块身份需要包含前面的完整前缀、模型/适配器、位置和必要的多模态信息；共享环境还要考虑租户隔离。引用仍为正的块不可任意覆盖。

## 三、计算与带宽：Prefill/Decode 为什么常有不同瓶颈？

标准密集注意力的 Prefill 处理 S 个 Prompt Token，单层注意力主要算术量为：

\[
\Theta(S^2 H_qd_h);
\]

有 KV Cache 的 Decode 单步面对 T 个历史 Key，单层为：

\[
\Theta(TH_qd_h),
\]

另需经过模型稠密层。连续生成 G 个 Token，累计历史交互数与：

\[
\sum_{j=0}^{G-1}(S+j)=GS+\frac{G(G-1)}{2}
\]

成比例（假设全量因果注意力，不使用滑窗/稀疏压缩）。

用 Roofline 作初步判断：若一次操作实际执行 F FLOPs、从主存搬运 M bytes，算力 \(\Pi\)、有效带宽 W，则：

\[
\boxed{t\gtrsim\max(F/\Pi,M/W)}
\]

小 Batch Decode 反复读取大模型权重，可能偏带宽受限；较大 Prefill 能重复利用权重，通常更偏矩阵乘法计算。这里的“通常”不能替代 GPU Profiler：不同硬件、Batch 和算子会改变瓶颈。

**理想权重侧例子：** 7B BF16 权重约 14 GB；若一次加载能服务 1 个 Decode Token，权重读取摊销约 14 GB/token；若能服务 16 个 Token，理想摊销约 0.875 GB/token。真实读取还涉及 KV、缓存层级、Kernel、并行与竞争，不等于实际测得 HBM Bytes。

## 四、调度：更高吞吐不一定降低用户延迟

Continuous Batching 让已完成的请求在迭代边界退出，新请求按容量加入；Chunked Prefill 让长 Prompt 分段进入每轮 Token Budget。调度至少要同时满足：

\[
\sum_{i\in \text{Decode}}x_i+\sum_{j\in\text{Prefill}}c_j\le K_{\text{step}},
\]

以及最大活跃序列数、KV Block Pool 容量约束。这里 x_i 通常是 0/1，c_j 是安排的 Prompt Token 数。**每轮新处理 Token 数和已累计缓存的历史 Token 数不是一个量。**

若持续优先 Decode，可保护正在流式输出的 TPOT，却可能让新 Prefill 排队、拉高 TTFT。抢占还可能产生 KV 重算或迁移成本。

从用户角度定义 TTFT 为到达到首 Token 的时间；对产生 G>=2 个 Token 的请求：

\[
\mathrm{TPOT}=\frac{t_{\text{last}}-t_{\text{first}}}{G-1},\qquad
\mathrm{E2E}=\mathrm{TTFT}+(G-1)\mathrm{TPOT}.
\]

稳态 Little 定律 \(\bar L=\lambda W_{\text{sojourn}}\) 描述平均系统内请求数、完成到达率及逗留时间的关系；不能把 M/M/1 的简单延迟公式当作实际 LLM GPU 的精确预测。

若同时要求 \(\mathrm{TTFT}\le a,\mathrm{TPOT}\le b\)，可定义**Goodput** 为每秒同时满足两项门限的完成请求数（需明确失败/单 Token 请求处理规则）。输出 Tokens/s 较高而 SLO 违约更多时，Goodput 可能下降。

**演示：** 某请求 TTFT=0.5 s，产生 21 个 Token，平均后续 TPOT=0.08 s，则端到端历时为 \(0.5+20\times0.08=2.1\) s。优化 Prompt 阶段不必然改变后续 Token 间隔，反之亦然。

## 五、把五种优化放进同一张资源表

| 优化 | 主要作用点 | 不会自动改变的事情 | 典型代价或风险 |
|---|---|---|---|
| Continuous / Chunked Batching | 每轮请求接纳、排队与算子利用率 | 同一请求的自回归顺序 | TTFT/TPOT 权衡、KV 竞争 |
| Paged KV / Prefix Caching | 动态物理分配、合法前缀计算复用 | 精确密集 Attention 的历史交互数量 | 内碎片、页表、缓存身份/隔离 |
| KV INT4/FP8、Offloading | KV 容量、驻留层级、潜在传输字节 | 新 Query 对历史信息的依赖 | 精度、解量化、PCIe/网络搬运 |
| W4A16 / W8A8 / FP8 权重量化 | 权重读取、某些算子效率 | 已有 KV 的位宽（若未另行量化） | 输出误差、Scale、Kernel 回退 |
| Speculative Decoding | 减少昂贵的**顺序** Target 验证轮次 | Draft 的运行成本与正确的采样条件 | 接受率低、额外 FLOPs、KV 回滚 |

归纳它们的不同资源目标：省 **HBM 容量**、省 **HBM 带宽**、省 **GPU FLOPs**、省 **串行关键路径**、改善 **排队和尾延迟**。任何两个目标都不能不经分析就画等号。

**量化与精度**：权重与激活的线性层误差满足

\[
(X+\Delta X)(W+\Delta W)-XW
=X\Delta W+\Delta XW+\Delta X\Delta W.
\]

对 KV 量化，Key 误差影响 Attention Score，Value 误差影响加权输出；必须独立评估模型质量。压缩为四分之一 Payload，不等于整个 Serving 显存四分之一，更不等于四倍加速。

**Speculative Sampling 精确性**：在同一条件前缀下，目标分布 p 与草稿分布 q 的标准接受率是

\[
a(x)=\min(1,p(x)/q(x)),
\]

首次拒绝后的修正分布是

\[
r(x)\propto[p(x)-q(x)]_+.
\]

接受路径贡献 \(\min(p,q)\)，拒绝修正贡献 \([p-q]_+\)，两者合起来恰好是 p。在每位置近似接受率 \(\alpha\)、草稿长度 \(\gamma\) 的简化条件下，

\[
\mathbb E[K]\approx\sum_{j=0}^{\gamma}\alpha^j.
\]

但实际加速还要支付 \(\gamma\) 次 Draft、Target 并行验证及 KV/调度成本，可能不加速，特别是高负载时。

## 六、两个系统场景，先诊断再选择优化

**场景 A：少量长 Prompt，多个请求重复相同公开资料前缀。** 如果 p95 TTFT 较高，首先分解排队和 Prefill 时间，测完整块前缀命中、Chunked Prefill 对首 Token 的影响；不能简单假定降低权重位宽就能解决一切。如果前缀不同或缓存上下文不一致，Prefix Caching 也无法凭相似字符串直接复用 KV。

**场景 B：许多短 Prompt、长输出的高并发会话。** 如果 p95 TPOT 高且 HBM 带宽紧张，应看 Decode Batch、权重访存和 KV 流量；W4A16、GQA、KV 量化或适配的推测解码值得按瓶颈比较。若 GPU 早已饱和，额外 Draft 计算甚至可能降低 Goodput。

两个场景都要对比**用户实际延迟与模型质量**，不能根据技术名称直接做优先级排序。

## 七、统一实验：什么叫“同质量下真正加速”？

~~~mermaid

  A["固定 Target、Tokenizer、采样设定、硬件和请求流"] --> B["按短/长 Prompt、输出长度与并发分组"]
  B --> C["记录 Target-only 基线：TTFT/TPOT、Goodput、HBM/Profiler"]
  C --> D["只改变一个因素：Batch / Cache / KV精度 / W精度 / Spec"]
  D --> E["检查分布或输出质量、有效 KV 前缀、Kernel 是否真的启用"]
  E --> F["开放到达率测试：排队、p95/p99、SLO、失败/OOM"]

  G -->|否| H["重新定位瓶颈，保留负面结果"]
~~~

一个最小可复现实验矩阵：Prompt 128/4096/16384、输出 32/256、低/高到达率、独立/重复前缀；固定模型、请求到达时间与采样，分别测基础推理、Continuous Batching、Prefix Caching、量化、Speculative Decoding。硬件上不支持的路径要如实报告，不能把 Kernel fallback 当成目标方案。

至少记录：请求级 p50/p95/p99 TTFT/ITL、输出 Token/s、Requests/s、双 SLO Goodput、队列时间、预填/解码 GPU Kernel 耗时、HBM 峰值与流量、KV 命中、量化误差/任务准确率、Draft 接受率及所有失败请求。区分**开环到达率**与闭环固定并发，防止因压测端自动放慢提交速度而掩盖排队。

## 八、本周最容易犯的六个错误

1. “KV Cache 消除了对历史 K/V 的读取”：错，它避免历史网络重算，但新 Query 仍访问历史信息。
2. “PagedAttention 把精确密集 Attention 变成 O(1)”：错，它主要改变存储与寻址。
3. “KV 命中率高说明每轮 Decode 更快”：Prefix 命中主要减少重复 Prefill，不能直接推出 TPOT 收益。
4. “INT4 就是全服务四倍省显存/四倍加速”：元数据、未量化部分、KV、Kernel 和带宽都要算。
5. “Speculative Decoding 的输出一定逐字等于独立 Target-only 采样”：精确方法保持概率分布，不保证两个独立随机样本相同。
6. “最高 Tokens/s 的设置就是最佳在线配置”：还必须考察质量、TTFT/TPOT 尾部、Goodput、公平与失败率。

**经典可推导部分**：KV 维度与容量、因果 Attention 算术阶、Roofline 下界、Little 定律条件、拒绝采样概率守恒。**具体研究/实现部分**：PagedAttention、Orca、Sarathi-Serve、各量化方案和 Speculative Serving 的性能改善都需要指定版本、模型、GPU、Kernel 及工作负载，不能把论文实验的倍数当普适常数。

### Lv1（15 分）｜优化机制与性能指标的边界

**考点：**优化机制与性能指标的边界；**预计用时：**2 分钟；**题型：**单选。

一个在线推理服务的许多请求共享很长的固定 Prompt，当前观察到 TTFT 高但 TPOT 尚可。关于系统优化与可验证结论，哪项判断最严谨？

- A. 只要开启 Prefix Caching，新 Query 的 Decode 就无需访问任何历史 KV，因此 TTFT 和 TPOT 都必然等比例下降。
- B. 应先分解排队与 Prefill 耗时，检查前缀完整性、缓存身份和真实命中；安全前缀复用可能减少重复 Prefill，但不保证 TPOT 同比改善。
- C. 只要将模型权重转成 INT4，TTFT、TPOT 和所有请求的端到端延迟都会严格缩小四倍。
- D. 只要采用 Continuous Batching，所有请求就都不会排队，并且同一请求的未来 Token 可同时生成。

**提示（不泄题）：**将“省去重复 Prefill”“更快读取模型权重”和“改变请求调度”分开分析，注意两个延迟指标的组成。

### Lv3（25 分）｜算术复杂度、Serving 竞争、缓存与精确采样的多步推理

**考点：**算术复杂度、Serving 竞争、缓存与精确采样的多步推理；**预计用时：**6 分钟；**题型：**多选。

考虑标准全量因果注意力的本地部署 LLM Serving，采用正确实现并明确所述前提。以下哪些判断成立？（多选）

- A. 增大 Decode Batch 可能改善模型权重访问的单位 Token 摊销，但会增加同时驻留的请求状态，并可能改变单请求时延。
- B. Paged KV 通过物理块映射改善内存分配和共享，本身不会把一个新 Query 与 T 个历史 Key 的稠密交互从 Θ(T) 变成 Θ(1)。
- C. 如果请求的 Prefix Cache 命中率达到 90%，则其后续每个 Decode Token 所需的 Key-Value 读取也严格减少 90%。
- D. KV INT4 和 Weight-only INT4 压缩不同的张量，二者不能直接用同一个“模型全内存缩小四倍”结论评价。
- E. 精确 Speculative Sampling 能在正确条件分布和接受—残差修正规则下保持目标采样分布，但其额外 Draft 负载仍可能使高并发 Goodput 下降。
- F. 只要模型每秒输出 Token 数提高，双重 TTFT/TPOT SLO 下的合格请求数每秒就必然提高。

**提示（不泄题）：**分别考虑权重读摊销、历史注意力算术、前缀复用的阶段、被压缩的张量、采样分布正确性以及 Goodput 定义。
