# 计算机体系结构 · 第18课
## 投机窗口与关键路径：分支解析延迟、ROB容量和安全检查放置

**2026年11月6日｜第3周第4课｜预计18分钟**

第15课讨论错误路径留下的微架构痕迹，第16课讨论间接目标预测与Retpoline，第17课区分了CET的架构控制流完整性与预测器隔离。今天不再重复防护术语，而是把问题放进**时间线和资源上界**：分支还要多久才能解析？这段时间里能够容纳、执行多少年轻指令？如果安全检查放置不合理，为什么“插了屏障”也不一定有效？

本课特别区分四个不同对象：**投机窗口长度、错误路径分配的指令数、已发出的微架构请求、最终架构提交**。它们相关，但绝不能直接画等号。

## 一、动机：Squash前哪些活动已经发生？（2分钟）

考虑边界检查后的数据消费：

~~~text
B0: if (index >= length) goto reject
L1: x = array[index]
I2: y = transform(x)
L3: z = dependent_read(y)
~~~

正常架构路径不允许越界读取。但当B0等待尚未返回的length，前端可能暂时预测“合法”，沿错误路径继续取指。B0后来判定应拒绝，处理器通过ROB、RAT与Free List恢复正确架构状态；然而错误路径发出的缓存访问不一定像寄存器映射那样完整回滚。

**注意安全上的两个不同断言：**“微架构状态可能变化”不等于“秘密必定泄漏”。后者还要求受到保护的信息、观察者、可区分的信号，以及具体的威胁模型。这里只对硬件执行顺序建模，不设计攻击代码。

~~~mermaid
flowchart TD
    P["预测B0并选择下一PC"] --> Y["年轻指令Fetch/Rename/分配ROB"]
    P --> G["条件操作数等待"]
    Y --> E["部分年轻指令Issue/Execute"]
    E --> M["可能发出Cache/TLB访问"]
    G --> R["分支真实结果解析"]
    R --> S["Squash错误路径、Redirect"]
    S --> A["恢复PC、RAT、Free List、GHR"]
    A --> C["正确路径按序退休"]
    M -. "微架构变化未必随Squash撤销" .-> O["另做观察通道分析"]
~~~

## 二、精确定义时间窗口与容量上界（2分钟）

设：
- \(t_p\)：分支作出预测的周期；
- \(t_y\)：错误路径第一条年轻指令可以开始Rename的周期；
- \(t_r\)：分支真实结果解析并开始恢复的周期；
- \(W_R\)：Rename宽度，单位条/周期；
- \(R_f\)：这次错误路径可使用的ROB空闲条目数，题中暂视为固定；
- \(N_y\)：恢复之前实际成功分配ROB的错误路径年轻指令数。

**本课采用的离散约定**：周期 \(t_y,t_y+1,\ldots,t_r-1\) 可以Rename，周期\(t_r\)开始恢复。因此最多有\(\max(0,t_r-t_y)\)个可用于分配的周期。

仅考虑Rename和ROB约束：

\[
\boxed{
N_y\le\min\{R_f,\;W_R\max(0,t_r-t_y)\}.
}
\]

**这是必要上界，不是执行数量。** Fetch实际供给、Issue Queue、LSQ容量、运算依赖以及恢复逻辑可能让真实\(N_y\)更小。如果ROB中还有其他在途工作，空闲容量也会动态变化，因此固定\(R_f\)是教学简化。

另有两个时间量不能混用：

\[
W_{pred}=t_r-t_p
\]

表示从预测到解析的区间；真正允许年轻指令分配的区间从\(t_y\)开始，通常更短。对于Cache等微架构副作用，需要追踪的是某次请求的**发出时刻** \(t_{touch}\)，而不仅是操作数返回或指令完成的时刻。

### 数值例题：是ROB先满，还是分支先解析？

设\(t_y=11\)，\(W_R=3\)，\(R_f=38\)。原分支在周期27解析，允许Rename的周期为11至26，共16个周期。仅按宽度可分配48个，但ROB只能容纳38个，所以有\(N_y\le38\)。

如果提前到周期18解析，则可Rename周期为11至17，共7个周期，宽度至多21，\(N_y\le21\)。这解释了为什么**缩短分支解析时间可能减少错误路径占据的窗口**。

然而，倘若敏感请求在周期15就已经发出，周期18才解析仍然晚于该请求。不能由“可分配上界下降”直接推出没有可观察微架构效果。

## 三、分支解析为什么可能受很长的依赖链约束？（2分钟）

一条分支的判断值不一定已在寄存器中就绪：

~~~text
L0: r1 = LOAD [length_pointer]  # 可能发生L2/L3 Miss
I1: r2 = compare(index, r1)
B0: branch_if_invalid(r2)
~~~

以依赖有向无环图\(G=(V,E)\)表示这些指令，\(\ell(v)\)为操作的延迟。无资源冲突的理想最早完成时间满足：

\[
\boxed{
F(v)=\ell(v)+\max_{u\in pred(v)}F(u)
}
\]

对没有前驱的节点，从其允许开始的时刻计起。沿着到B0的最长依赖路径求和，就是分支解析的**关键路径下界**。它不等于真实时间，因为实际还可能受执行端口、Cache排队与Wakeup/Select限制。

例如在一个明确的模型中，长度Load的结果需等待12周期、比较2周期、分支操作1周期，那么即使预测器100%准确，这条依赖链也不能凭空缩短。

改进手段可以是缩短合法公共数据的访存延迟、优化比较的指令链，或者在语义允许时提前准备条件。**加大BTB或让方向预测更准，并不自动减少真实条件计算延迟。**

## 四、ROB更大，是否代表危险窗口必然更大？（2分钟）

增加ROB容量有利于保留更多独立工作、隐藏长延迟，但带来两种互相独立的影响：

1. **性能方面**：若原来ROB经常阻塞Rename，容量增加可能提升平均IPC；
2. **投机方面**：在某些依赖与资源条件下，也允许更多错误路径操作进入并推进。

不能把两者简化成“ROB越大，必然更不安全”。已分配40条年轻指令，不等于40条都Issue，不等于40个Cache请求，更不等于40字节秘密泄漏。实际还受Load端口、Cache、LSQ、条件依赖及安全检查限制。

第13课推导过稳态Little定律：

\[
\bar N_{ROB}=IPC\,T_{ROB},
\qquad
IPC\le\frac{R}{T_{ROB}}.
\]

这里的\(T_{ROB}\)包括分配到释放的全部驻留周期，不是ALU执行延迟。**稳态平均占用公式**与上一节的**一次错误分支的瞬时容量上界**不能直接互换。

反例：一条高度串行的Load依赖链已经占据关键路径，增加ROB却没有更多独立请求可发，实际IPC可能几乎不变；若增大的ROB使访存并发增加，\(T_{ROB}\)本身也可能改变。

## 五、检查与投机屏障：为什么位置是安全证明的一部分？（3分钟）

抽象比较：

~~~text
方案A：屏障在边界检查前
barrier
if (index_invalid): reject
consume_sensitive_index(index)

方案B：在检查之后、敏感消费之前
if (index_invalid): reject
LFENCE
consume_sensitive_index(index)
~~~

讨论方案B时，明确限定为**符合Intel关于LFENCE投机顺序保证、且编译器实际生成并保留所需指令顺序的系统**。Intel关于Bounds Check Bypass的指导指出，对于适用路径，应在边界检查后、受检查数据参与危险消费前放置相应屏障。屏障放在检查之前，并不自动保证检查之后的指令不会越过尚未解析的判断。

从执行图角度，目标不是“源码里面出现了LFENCE”这个文本事实，而是建立：
\[
\text{检查条件已正确完成}
\quad\prec\quad
\text{危险敏感访问的发出}.
\]

审查时要检查实际生成的机器码、异常路径、编译器保序和特定处理器的保证。不要以“Load后来被Squash”代替对已发出的微架构请求检查。

另一条方法是**经过验证的地址范围约束**（例如安全索引约束）：无论瞬态路径如何执行，实际形成的访问地址都必须属于经证明合法的集合。它可能保留更多独立计算，但前提是机器级数据依赖与范围证明都真实成立。不能把某个普通源码\(if\)改写成位运算，就无条件宣称它是安全屏障或适用于所有CPU。

### 一个反例

假设危险请求在周期17发出，分支原来周期29才解析，优化后周期21解析。窗口明显缩短，但请求仍比检查解析早4周期。**降低暴露窗口的机会**不等于**证明危险请求不可发生**。

## 六、关键路径与屏障范围：保护不应盲目阻塞所有工作（2分钟）

区分两条年轻工作链：

- \(C\)：受边界检查约束的敏感数据消费；
- \(U\)：与检查无关、使用公开输入的独立计算。

如果两条链本可以重叠，只有\(C\)需要等待检查完成，那么一个过于宽泛的屏障可能同时延迟\(U\)，损失ILP。

~~~mermaid
flowchart LR
    G["边界检查解析"] --> C["敏感消费C"]
    U0["独立公开计算"] --> U1["后续计算U"]
    C --> Z["汇合"]
    U1 --> Z
    G -. "宽泛屏障可能额外阻止U" .-> U1
~~~

在理想独立资源、可重叠执行的情况下，汇合时间可能由\(\max(T_C,T_U)\)决定，不是\(T_C+T_U\)。一旦插入屏障或造成资源争用，实际依赖图和执行顺序发生变化，必须重新测量。

因此设计空间有一个真实的**安全—延迟—吞吐权衡**：屏障可能更容易建立所需顺序，但阻止某些安全且独立的年轻工作；精确的地址约束可能减少额外等待，但需要更强的实现和验证条件。**不应以性能较好替代安全证明，也不能以性能较差证明安全充分。**

## 七、建立可检查的性能反事实（2分钟）

设：
- 退休指令数为\(N\)；
- 基线\(CPI_0\)；
- 每条退休指令中受保护操作占比\(f_g\)；
- 每次保护新增平均\(d\)周期；
- 新增周期全部可见、互不重叠；
- 指令数与频率不变。

则新增总周期：
\[
\Delta C=Nf_gd.
\]

因此：
\[
\boxed{CPI_{new}=CPI_0+f_gd.}
\]

固定频率与指令数：
\[
\frac{T_{new}}{T_0}=\frac{CPI_{new}}{CPI_0}
=1+\frac{f_gd}{CPI_0}.
\]

**手算例**：\(CPI_0=1.25,f_g=0.10,d=2\)，新CPI为1.45，执行时间相对基线增加\(0.20/1.25=16\%\)。但IPC相对变化要以\(IPC_0\)为分母，不能也写成“下降16%”。

这里的\(d\)是教学假设，不是任何真实CPU上LFENCE的固定时延。屏障可能与已有Stall重叠，也可能改变Issue、ROB占用和前端供给；不能把同一周期的ROB Full、Branch Recovery与Fence Stall简单重复相加。

## 八、需要哪些Trace才能验证？（1分钟）

一份可信诊断报告，最好为同一实验ID保留：

| 字段 | 能说明的问题 |
|---|---|
| 预测时刻、分支PC、预测/真实方向 | 错误路径如何出现 |
| Rename/Issue/Squash时间 | 在途工作与恢复边界 |
| ROB/LSQ容量和占用 | 是否存在资源反压 |
| 敏感访问请求**发出**时刻 | 解析前是否存在微架构请求 |
| 编译后检查/屏障的机器码位置 | 源码意图是否实际落实 |
| 架构输出、异常和状态恢复 | 精确提交是否正确 |
| 无额外profiling的重复运行 | 真正端到端性能变化 |
| CPU/编译器/内核/防护模式 | 结论适用范围 |

“代码通过边界检查测试”仅证明指定架构功能行为；“错误路径没有退休”仅证明一类提交约束。侧信道防护还应在明确威胁模型与观察条件下单独评估。

**TSO提醒**：Store从ROB按序退休，不等于瞬间对全部核全局可见。Store可能仍驻留Store Buffer；本核较年轻Load与该Store的转发规则、其他核看到写的时刻，是不同的排序约束。控制流的Spectre窗口与TSO的Store Buffering也不是同一问题。

## 九、总结与下一讲（1分钟）

四个概念不能画等号：
\[
\boxed{\text{分支投机窗口}\ne\text{已分配年轻指令数}\ne\text{微架构请求数}\ne\text{架构提交结果}.}
\]

缩短分支关键路径能减少某些投机机会，但不能自动撤销更早的请求；增加ROB可能改善ILP，却无法保证性能线性提高；合适的检查后屏障与经验证的地址约束建立不同的安全/性能权衡，必须在实际硬件、编译器和威胁模型下验证。

## Lv3｜容量模型、瞬态观察与TSO边界｜25分｜多选｜预计5分钟

关于错误路径容量、投机屏障和内存模型，下列哪些判断正确？

**A.** 错误路径进入ROB的指令数减少，并不能单独证明再没有秘密相关的Cache/TLB效果。

**B.** ROB按序退休保证错误路径年轻指令不退休，因此其微架构访存请求在物理上绝不可能发出。

**C.** 在题目限定的Intel LFENCE及编译器保序保证下，将屏障放在已完成的边界检查之后、危险消费之前，可以约束后续投机越过检查。

**D.** 在检查之前加屏障，就必然阻止检查之后的所有危险操作越过尚未解析的检查。

**E.** 提前解析分支可能缩短某些危险投机窗口，但若敏感请求更早已发出，不能由此直接证明安全。

**F.** TSO要求Store一旦从ROB退休便立即同时对所有核全局可见。

## Lv4｜关键路径、屏障验证与性能反事实｜40分｜开放推导｜预计10分钟
