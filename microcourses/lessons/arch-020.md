# 计算机体系结构 · 第20课
## 预测器隔离与系统级代价：上下文切换、SMT共享资源与安全性能取舍

**2026年11月8日｜第3周第6节新课｜预计18分钟**

过去五节课从错误路径微架构痕迹一路讲到Retpoline、CET、投机窗口和反事实安全测量。今天换一个观察尺度：**即使单条指令、单次Squash都正确，操作系统在两个不互信程序之间切换，或将两程序放在同一颗支持SMT的物理核心上执行时，预测器历史与共享硬件资源怎样影响隔离和性能？**

本课请记住一个核心区别：**跨时间（time-sharing）与跨兄弟线程（SMT concurrent）不是一个边界。** IBPB、STIBP、eIBRS及调度隔离各解决不同问题；它们也都不能自动证明不存在Cache侧信道。

## 一、动机：同一个CPU核心有几种“共享”？（约2分钟）

考虑物理核心P，提供两个逻辑处理器LP0与LP1。A和B是不互信租户。

~~~text
场景一：同一逻辑处理器，分时运行（跨时间）
LP0:   A ──────| context switch |────── B
LP1:   不考虑或运行其他工作

场景二：同一物理核心，SMT同时运行（跨兄弟线程）
LP0:   A ─────────────────────────
LP1:   B ─────────────────────────
          同一时间段竞争核心部分硬件资源

场景三：更强的空间隔离
物理核心P0: A             物理核心P1: B
仍需分析共享的更高层Cache、内存控制器等
~~~

场景一中的风险是：B开始运行时，硬件预测状态可能还含有A先前执行的影响。场景二中，即使不存在从A切换到B的时刻，两者仍可能同时使用物理核心中的部分预测或执行资源。

因此不能仅问“是否已经执行过预测器屏障”，还必须问：**屏障作用在哪个逻辑CPU、针对哪个预测机制、两个域是先后还是并行？**

~~~mermaid
flowchart TB
    A["两种不互信执行域 A / B"] --> Q{"关系"}
    Q --> T["同一逻辑处理器上的先后切换"]
    Q --> S["同一物理核心的SMT并发"]
    T --> P["评估IBPB / 预测域隔离 / 调度边界"]
    S --> U["评估STIBP或等效硬件保护、核心调度/SMT策略"]
    P --> V["分别检查安全覆盖与性能成本"]
    U --> V
    V --> C["仍需独立分析Cache等共享资源"]
~~~

## 二、准确理解四个机制的作用范围（约3分钟）

**IBPB（Indirect Branch Prediction Barrier）** 是针对间接分支预测影响的屏障机制。在适用x86处理器上，可用于某些不互信执行域之间的先后切换。它不是Cache全清空，也不是让Store立刻可见，更不是“执行一次后，所有逻辑线程从此隔离”。

**STIBP（Single Thread Indirect Branch Predictors）** 主要用于限制同一物理核心上SMT兄弟逻辑处理器之间的间接分支预测影响。其具体需求取决于处理器能力与系统启用的其他硬件缓解，例如Intel增强型IBRS的保护组合。它并不消除共享执行端口或Cache资源竞争。

**IBRS / enhanced IBRS（eIBRS）** 限制特定预测模式/特权级之间的间接分支预测影响。Intel增强型IBRS在相应模式下提供SMT相关的STIBP保护，但不能由此直接推出同模式域之间无预测风险，更不能推断BHI等历史影响或所有Cache侧信道都已消失。

**调度/核心隔离** 从时间或空间上限制不互信负载重叠：例如让两个租户使用不同物理核心，或对同核心SMT兄弟线程采取同信任域协同调度。它可以减少特定并发干扰，但更高层级的共享Cache和内存资源仍可能存在。安全性依赖威胁模型和硬件实际共享关系。

Linux的Spectre文档区分了IBPB针对不同用户进程的时间边界、STIBP针对SMT兄弟线程的隔离，以及BHI的历史输入风险；Intel指南说明eIBRS和按需IBPB的适用条件。这里不把任何机制讲成“万能防护”。

来源：Linux内核Spectre说明 https://docs.kernel.org/admin-guide/hw-vuln/spectre.html ，Intel推测执行缓解指南 https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/technical-documentation/speculative-execution-side-channel-mitigations.html 。

### 两个不能混淆的事件

**Context switch** 通常是OS调度器让某个逻辑CPU从线程/进程A切换到B，是否需要IBPB取决于安全域关系与系统配置，并非每次切换固定都执行相同屏障。

**VM-exit** 是虚拟化执行从Guest转向Hypervisor的事件。它可以在没有一般进程上下文切换的情况下发生。故仅依赖“进程切换时检查”不保证覆盖所有Guest→Host边界；针对具体VMM威胁需核查额外的VM-exit处理与硬件能力。Linux近期的VMSCAPE文档就专门解释这一点。来源：https://docs.kernel.org/admin-guide/hw-vuln/vmscape.html 。

## 三、为何IBPB不能取代SMT并发保护？（约2分钟）

设同一个物理核心的LP0在周期100执行一次IBPB，随后运行受保护域B；同时LP1上的不可信域A在周期95至180仍在运行。

~~~text
周期     90      100       120      150       180
LP0      旧任务──IBPB──────B──────────────────
LP1      A────────────────────────────────结束
                  ↑
                  IBPB并没有使LP1停止执行
~~~

这说明跨时间屏障与同时运行的兄弟线程影响不同。IBPB对适用预测状态提供时间边界，而并发兄弟线程可以继续参与物理核心资源活动；需要按CPU实际支持采用STIBP/等效硬件保护、调度隔离或其他措施。

反过来，只启用STIBP也不能自动当作所有跨时间安全域切换所需屏障的替代品。**应以具体CPU微码、OS缓解状态和信任边界决定组合。**

还要区分安全隔离和纯性能争用：两个合法SMT线程可能竞争前端带宽、执行端口、Load/Store资源、共享Cache；这通常首先表现为单线程时延变大，未必属于预测器注入漏洞。共享资源也可能与其他侧信道有关，但不能仅凭性能下降证明泄漏。

## 四、SMT为什么既能提高总吞吐，又能降低单线程IPC？（约2分钟）

单个物理核心在某周期可能有空闲的发射槽。一条线程被Cache Miss或数据依赖阻塞时，另一条线程可以利用这些槽，因此SMT有机会提高核心吞吐。

但当两条线程都准备好了大量工作，它们也会竞争共享执行资源。于是**总吞吐增加**和**每个线程吞吐降低**可以同时成立。

数值例子（纯教学假设）：

| 模式 | A IPC | B IPC | 总IPC | 解释 |
|---|---:|---:|---:|---|
| 只运行A | 2.4 | — | 2.4 | 独占核心 |
| 只运行B | — | 2.0 | 2.0 | 独占核心 |
| A/B同核SMT同时运行 | 1.6 | 1.3 | 2.9 | 总IPC比任一独占运行高，但每个线程变慢 |

不能把表中2.9与2.4直接换算成两租户完整任务的统一加速比。还要知道两者指令数、服务时间、工作量和完成条件。比较两条任务完成时间时，应分别计算A与B的进度，并明确是单租户延迟还是多租户总吞吐目标。

**适用边界：** SMT线程共享哪些单元、拥有多大配额、是否有动态优先级以及是否启用安全缓解，都因微架构不同。禁用SMT有可能降低总吞吐，并非“零成本安全选项”；同时启用SMT也不能不考虑安全域。

## 五、性能账本：为什么上下文切换频率决定IBPB成本？（约3分钟）

用一个简化、可反驳的模型：

- \(N\)：完成固定工作量所退休的架构指令数；
- \(CPI_0\)：未计入本节附加开销的基线CPI；
- \(n_{\mathrm{sw}}\)：需要执行某种IBPB的安全域切换次数（不等于所有上下文切换次数）；
- \(c_{\mathrm{ibpb}}\)：每次屏障的额外暴露周期数；
- \(f_i\)：需要考虑STIBP成本的间接分支指令占比；
- \(d_{\mathrm{stibp}}\)：本模型中每条相关分支新增的平均周期；
- \(C_{\mathrm{other}}\)：调度、资源竞争等额外周期。

如果全部新增成本相互独立且完全暴露，则：

\[
C_{\mathrm{new}}
= NCPI_0+n_{\mathrm{sw}}c_{\mathrm{ibpb}}
+Nf_id_{\mathrm{stibp}}+C_{\mathrm{other}}.
\]

两边除以N：

\[
\boxed{
CPI_{\mathrm{new}}
=CPI_0+\frac{n_{\mathrm{sw}}}{N}c_{\mathrm{ibpb}}
+f_id_{\mathrm{stibp}}+\frac{C_{\mathrm{other}}}{N}
}
\]

这不是某一CPU的硬件定律，而是明确条件下的**增量周期账本**。

### 数值例题

假设一段固定工作量：

\[
N=1{,}200{,}000,\quad CPI_0=1.10.
\]

需要保护的切换有2400次，每次额外80周期；间接分支占5%，采用的缓解在此教学模型中使每条增加1.5周期；忽略其他额外成本。

基线周期：

\[
C_0=1{,}200{,}000\times1.10=1{,}320{,}000.
\]

切换附加周期：

\[
C_{\mathrm{IBPB}}=2400\times80=192{,}000.
\]

分支附加周期：

\[
C_{\mathrm{STIBP}}=1{,}200{,}000\times0.05\times1.5=90{,}000.
\]

所以：

\[
C_{\mathrm{new}}=1{,}602{,}000,\qquad
\boxed{CPI_{\mathrm{new}}=1.335}.
\]

固定频率、相同指令数时，运行时间增幅：

\[
\frac{1.335-1.10}{1.10}\approx21.36\%.
\]

这不是IBPB或STIBP的真实测量数据。真实成本可能随CPU型号、分支结构和SMT负载变化，也可能与其他停顿重叠，不能无条件使用上述数值估算产品性能。

### 为什么不能重复加算？

如果IBPB发生在原本因Cache Miss而停顿的时间里，墙钟执行时间新增未必等于微基准测得的独立屏障延迟。反过来，预测状态处理可能影响后续分支错误率，产生间接成本。

正确的报告应该同时给出总墙钟周期/任务完成时间、退休指令数、上下文切换数、预测失误率、共享资源占用及明确的时间区间归因，而不是简单把多个“Stall计数”全部相加。

## 六、一个更难的设计抉择：少切换、禁用SMT还是硬件保护？（约2分钟）

考虑两个租户各自有SLO。设计人员可能采用：

- **策略一：** 维持SMT，按现有CPU/OS安全缓解配置使用所需预测器隔离，并衡量单线程SLO与总吞吐。
- **策略二：** 在较强隔离需求下采用同信任域核心调度或独立核心部署，减少不互信SMT并发，再测量吞吐损失、排队延迟与资源利用率。

这不是凭一个性能公式就可以决定的选择。需要首先确认攻击者能力、租户信任边界、CPU型号/微码、是否支持eIBRS和相关硬件隔离、系统是否实现所需切换屏障。

随后进行**等功能、等输入、等负载强度**的A/B测试，分别看每租户P50/P99延迟、总吞吐、公平性，以及预测相关可观察行为。

即使把A/B放在不同物理核心，更高层共享的Last-Level Cache、内存控制器或互连仍可能带来争用；不能声称“分核=绝对无侧信道”。

### 三项验证，不是一个安全开关

1. **能力：** CPU硬件、微码和Kernel是否支持相关机制。
2. **启用：** 当前系统/进程究竟运行了哪些缓解，包括何时执行屏障及SMT调度政策。
3. **威胁覆盖：** 这些机制对指定攻击面是否充分；是否还需BHI、RSB、Cache通道等独立分析。

有权限的Linux主机上可以做只读检查：

~~~bash
cat /sys/devices/system/cpu/vulnerabilities/spectre_v2
cat /sys/devices/system/cpu/smt/active
lscpu | grep -E 'Thread\(s\) per core|Core\(s\) per socket|Model name'
~~~

这些输出是能力与缓解状态线索，不是数学意义上的全部安全证明。不要为对照实验随意关闭生产主机必需的安全保护。

## 七、与TSO的联系：最后再次分清“两个缓冲”（约1分钟）

预测器历史残留与Store Buffer保留已退休写入，名字都含“buffer”，但研究的问题完全不同。

在常见的TSO Store Buffering例子中：

~~~text
初始 x=y=0
Core 0: STORE x=1 ; r0=LOAD y
Core 1: STORE y=1 ; r1=LOAD x
~~~

每个核可能让Store先在本核缓冲中等待传播，再读取另一个地址，因此在TSO模型下 \((r0,r1)=(0,0)\) 可以合法。这里**Store已经可按序退休，但不必已经对其他核可见**。

这是内存模型允许的架构观察，不是分支预测错误，不是IBPB能“修复”的问题，更不能直接证明秘密泄漏。

特别强调两种“先后”：
- **同核按序退休**只约束架构提交边界；
- **跨核可见性/内存排序**决定其他核何时能够观察Store。

第五周将深入SC/TSO与一致性、全局可见性关系。

## 八、反例与适用边界（约1分钟）

**反例一：** 在LP0切换时执行IBPB，并不能推出LP1上同时运行的不可信线程已经停止影响所有共享资源。

**反例二：** 只因CPU支持eIBRS，不能断言BHI或所有同模式历史风险不存在；更不能以此宣称Cache保密性已证明。

**反例三：** 禁用SMT可能减少某些共享风险，却可能降低整机吞吐并增加排队时延。安全选择应以威胁模型为先，性能量化为后。

**反例四：** VM-exit不要求发生一般OS进程上下文切换；只监控context switch可能漏掉重要安全边界。

**反例五：** 单线程IPC下降不一定意味着物理核心总吞吐下降。需要分别核算每租户完成时间与总任务量。

## 九、小结与下一讲（约1分钟）

今天建立三个独立判断：

\[
\boxed{\text{时间隔离}\ne\text{SMT并发隔离}\ne\text{所有共享资源安全}}
\]

并建立性能成本模型：

\[
\boxed{
\Delta CPI
=\frac{n_{\mathrm{sw}}}{N}c_{\mathrm{ibpb}}
+f_id_{\mathrm{stibp}}+\frac{C_{\mathrm{other}}}{N}
}
\]

必须带上“不重叠、固定工作量、固定频率”的前提；真实系统仍要做端到端测量与安全覆盖核查。

## Lv1｜跨时间与SMT兄弟线程预测器隔离
**15分｜单选｜预计2分钟**

同一物理核心有两个SMT逻辑线程T0和T1，分别运行不互信租户A、B；同时A与B也可能在同一逻辑线程上分时切换。以下哪项最准确地区分IBPB与STIBP？

**A.** IBPB专用于将已退休Store立即传播给其他核，STIBP专用于清空ROB。

**B.** IBPB可用于规定的先后执行域切换时的间接分支预测影响隔离；STIBP主要用于限制同时运行的SMT兄弟逻辑线程之间的间接分支预测影响，需结合CPU能力与系统配置。

**C.** 只要切换进程时使用IBPB，就自动消除与另一SMT兄弟线程的全部并发微架构干扰。

**D.** STIBP保证所有Cache侧信道被消除，因此SMT上无需考虑其他安全边界。

## Lv2｜IBPB与STIBP联合成本计算

## Lv3｜SMT性能、预测器隔离与TSO边界
**25分｜多选｜预计5分钟**

关于跨上下文预测状态、SMT和内存可见性，选出所有正确说法。限定讨论文中描述的适用x86硬件行为与Linux安全配置。

**A.** 不互信执行域在同一逻辑处理器上分时运行时，残留分支预测状态可能形成跨时间影响；适用的IBPB可以在规定边界降低这种影响。

**B.** 只在T0上执行一次IBPB，就能无条件隔离同一时刻仍运行在T1上的不可信兄弟线程的所有共享微架构状态。

**C.** 两个SMT线程共享部分核心资源，因此单线程IPC可能下降，即使两线程合计吞吐有所提升。

**D.** 只要启用eIBRS，就无需考虑任何BHI、同模式预测历史或者Cache观察通道。

**E.** Store从ROB退休仍可能驻留在Store Buffer中；这属于内存排序/可见性问题，不能用IBPB是否执行来判断。

**F.** 减少上下文切换次数必然改善每个租户的延迟、公平性及所有共享资源竞争，不需看负载。
